### Data Flow
```
API Request (POST /v1/start)
  → Initialize accounts, fund, deploy contracts
  → Start workers:
      Rate Limiter → Pipeline.Execute() → ReserveNonce → Build TX → Sign → Encode
        → Sender.SendAsync() (semaphore-bounded, 2K concurrent)
          → Callback: Commit nonce on success, Rollback on failure
  → Parallel streams:
      - Preconfirmation WS → latency tracking
      - Block metrics WS → MGas/s rolling window
      - L2 newHeads WS → gas/fill rate tracking
  → On stop: grace period → verify on-chain → persist to SQLite
```

## Data Model

### Schema Overview
SQLite with 5 tables. WAL mode for concurrent read/write. Models in `internal/storage/models.go` with camelCase JSON tags.

### Core Entities

#### test_runs
Primary model — 60+ fields covering test configuration, results, statistics, verification.
- **Key fields:** id, pattern, transactionType, durationMs, txSent/Confirmed/Failed, latencyStats, peakMgasPerSec, verification
- **Concerns:** Very wide table. JSON-serialized nested structs (latencyStats, environment, verification) stored as TEXT columns.

#### time_series
Metrics samples every 200ms during tests.
- **Key fields:** timestampMs, txSent/Confirmed/Failed, currentTps, gasUsed, mgasPerSec, fillRate

#### tx_logs
Individual transaction records.
- **Key fields:** txHash, sentAtMs, confirmedAtMs, preconfAtMs, status, nonce, gasTipGwei
- **Concern:** Can grow very large at high TPS (25K TPS × 60s = 1.5M rows per test). Memory limit of 200MB enforced.

#### verification
Post-test on-chain verification results.

#### incremental_snapshots
Checkpoint data during test runs.

### Data Health
- **Migration strategy:** None. Schema created via `CREATE TABLE IF NOT EXISTS`. No versioned migrations.
- **Constraints:** Minimal — primary keys exist, but no foreign key enforcement visible.
- **Sensitive data:** Private keys for test accounts are generated in-memory, not persisted. No PII.

## Load-Bearing Elements

These must not be changed without deep prior understanding.

| Element | Why Load-Bearing | Risk if Changed | Prerequisites Before Touching |
|---|---|---|---|
| Nonce reservation pattern (`internal/account/`) | Every TX depends on correct nonce ordering. Rollback/commit semantics prevent gaps at 25K TPS. | Critical — breaks all TX submission | Understand reservation→commit→rollback lifecycle, async callback ownership |
| Circuit breaker in `workers.go` | Prevents cascade failure when builder/node falls behind. Triggers nonce resync. | Critical — can cause nonce desync or infinite retry storms | Understand failure rate thresholds, resync mechanism, rate reduction |
| Rolling window MGas/s in `blockmetrics.go` | Primary performance metric. Dashboard and test results depend on this calculation. | High — incorrect metrics invalidate all test results | Understand 5-second window, minimum data requirements, freeze-on-stop |
| Streaming percentile calculation (`internal/metrics/`) | Reservoir sampling (Algorithm R) for O(1) memory percentiles. | High — wrong percentiles = wrong latency data | Understand reservoir sampling, accuracy guarantees |
| Async sender callback ownership | Nonce commit/rollback happens in async callback, not sync path. Prevents double-commit race. | Critical — race conditions at high concurrency | Understand why nonce is NOT committed before send, callback ownership |
| SQLite WAL mode + batch writes | Handles persistence at 25K TPS without blocking workers. | High — can cause write contention or data loss | Understand WAL concurrency model, batch transaction grouping |
| TX pipeline execution order | sign→send→callback is a strict pipeline. Reordering breaks nonce accounting. | Critical — nonce gaps, duplicate nonces | Understand full pipeline flow in `internal/pipeline/` |

## Survey Findings Summary

### What's Working Well
- **Refactor quality is high.** The monolith split was methodical (8 phased commits), preserved all functionality, and created clean file boundaries. Each file has a clear single responsibility.
- **Nonce reservation pattern** is well-designed for high throughput — local tracking with atomic reservation and async callback ownership.
- **Capability-based execution layer abstraction** scales cleanly to new node types without code changes.
- **Lower-level packages are well-tested** — ratelimit (100%), workload (98%), execnode (97%), pattern (86%), storage (81%).
- **API contract tests** validate JSON shapes and camelCase compliance — prevents dashboard breakage.
- **Performance is proven** — 25K TPS sustained with 100% confirmation rate. This is not aspirational, it's tested.

### Immediate Risks
- **Core orchestrator is untestable without interface extraction.** The `internal/loadgen` package (4,736 lines) calls concrete RPC/builder types directly. You can't unit test workers, init, or API handlers without mocking these.
- **RPC retry logic is effectively untested** (4% coverage). This is the network boundary — where things go wrong in production.
- **No migration framework** means schema changes require manual coordination. Acceptable now, will bite as the schema evolves.

### Recommended Next Steps
Before a `/cartographer` planning session:

1. **Decide: merge refactor branch first?** The current state is clean and functional. Merging gives a stable baseline before adding tests.
2. **Extract RPC/builder interfaces** — this unblocks all testing of `internal/loadgen`. Estimate: 2 days. This is the single highest-leverage change.
3. **Write tests for pure functions first** — `helpers.go`, `blockmetrics.go` math, `builder.go` parsing. These need no mocks and prove the refactor didn't break calculation logic.
